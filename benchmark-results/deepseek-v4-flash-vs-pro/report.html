#### 5.1 Authentication & Authorization
- Use JWT for stateless API authentication.
- Store refresh tokens in HttpOnly cookies for security.
- For permissions, check on every note operation: the note must exist, and the user must have the appropriate permission (view/comment/edit).

- **Conflict resolution**: Use Operational Transform (OT) or CRDTs. - Pick an editor that supports real-time collaboration: e.g., `Slate` with its Yjs plugin, or `TipTap` (ProseMirror) with `y-prosemirror`.

#### 5.4 Search
- Use PostgreSQL full-text search for simplicity: `to_tsvector` on title and content.

#### 5.5 Version History
- Whenever a note is saved (autosave every 30 seconds or on manual save), store a snapshot in `note_versions` with the current revision number.
- Allow users to view past versions and restore them (by creating a new version from older snapshot).

#### 5.6 File Uploads

Do **not** drop the production table yet. In a failed migration, dropping/recreating is a last resort because it can turn a recoverable partial migration into permanent data loss. Recommended order of action: 1. **Stop further changes** - Stop the migration job/retries. - Consider putting the app into maintenance mode or temporarily blocking writes to affected tables. 2. **Take a backup/snapshot immediately** - Back up the database as it exists now, even if it is half-migrated. - Also identify the last known-good backup or point-in-time recovery target from just before the migration started. 3. **Find the exact failure point** - Read the migration logs and identify the exact statement that failed. - Determine which statements completed before the failure. - Check whether your migration framework wrapped the migration in a transaction. 4. **Understand your database’s DDL behavior** - **PostgreSQL:** DDL is generally transactional if run inside a transaction, so the failed migration may have rolled back cleanly. - **MySQL/MariaDB:** many DDL statements cause implicit commits, so the database may genuinely be in a partially migrated state. - **SQL Server:** many DDL operations can be transactional, but not all. 5. **Prefer rollback, restore, or a targeted repair** - If you have a verified pre-migration backup or PITR, restoring to just before the migration is often safest. - If only a few schema changes succeeded, write a small corrective migration to reverse or complete those specific changes. - If the migration failed because of bad data — for example duplicate values blocking a unique constraint — fix the data issue first, then retry safely. 6. **Only consider dropping/recreating if it is clearly safe** Dropping may be acceptable only if the table is new and empty, purely derived/cache data, or fully recoverable from a verified backup/rebuild process.
